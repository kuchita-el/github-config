# ADR 0004: Terraform module 構造の方針と類型プロファイル

## ステータス

提案中（2026-09-26、[#32](https://github.com/kuchita-el/github-config/issues/32)）

本 ADR は次の決定を置き換える。置き換えられた ADR の本文は変更せず、ステータス節に置き換えの旨を記す。

- [ADR 0001](0001-repository-resource-structure.md) 決定 §1 のうち、値の置き場所（`repositories` のフィールド既定値に preset を置く variable defaults パターン）と、per-repo override で全属性を上書きできるとする部分。`repository.tf` への1ファイル集約、`visibility` の必須化、決定 §2・§3 は引き続き有効である。
- [ADR 0005](0005-squash-only-merge-method.md) 影響節の「既存の per-repo override 機構は変更しないため、個別リポジトリで本方針から外す余地は残る」。`allowed_merge_methods` は本 ADR の全リポ共通値にあたり、外すには例外台帳への登録を要する。

## コンテキスト

設定種別（ラベル、Dependabot、Actions 権限、タグ保護など）を足す Issue が複数控えている。このまま進めると、次の問題が起きる。

1. 各 Issue が module 化の要否を独立に判断し、構成が揃わない。
2. [ADR 0001](0001-repository-resource-structure.md) のパターンを `github_repository` 以外のリソース型へどう広げるかが決まっていない。
3. module 化や root の分割を検討する条件が無く、判断が場当たりになる。

あわせて、次の方針が決まっている。

- private リポも、Ruleset 以外の設定の管理対象に含める（#4 の 2026-09-26 のコメント）。
- リポに類型プロファイルを1つ割り当て、類型ごとに設定の値を変える（#32 の 2026-09-26 のコメント）。

類型ごとの値をリポ単位で上書きできる構造（「類型既定値 → per-repo override」の2段）も検討したが、本リポの所有者（kuchita-el）が 2026-09-26 に次の方針を示した。

> repositoryのパラメータについてなんだけど、可能な限り個別のオーバーライドを許可するよりは、プロファイルごとの型にはめて使える運用にしたい。

この方針は、ADR 0001 の variable defaults パターン（すべての属性を `repositories` のフィールドとして per-repo で上書きできる）と両立しない。本 ADR はこれを受けて、値の置き場所と per-repo で変えられる範囲を定め直す。

## 決定

### 1. 単一 root module を維持する

- child module は作らない。root module は本リポ直下の1つ、HCP Terraform の Workspace は `github-config` の1つとする。
- 設定種別を足すときは、root 直下に設定種別ファイル（§5）を1枚足し、`for_each` で管理リポへ展開する。
- この構成は、§2 の条件が発火した場合にだけ見直す。

### 2. 構成を見直す発動条件

条件を3つの区分に分ける。分割の必要条件は区分 A の事象だけであり、区分 C の閾値を超えたことは分割の理由にしない。

**区分 A: root / Workspace の分割**（事象が起きたら分割を検討する Issue を起票する）

- **A-1**: 追加する設定種別の API が、GitHub App の権限（Administration: Read & write / Metadata: Read）を超える。App の権限を拡張する Issue の中で、別 App・別 Workspace へ分けることを代替案として必ず評価する。
- **A-2**: `github_owner` と異なる owner / Org（検証用のアカウントや Org を含む）の設定を管理対象に加える。本リポには dev / stg / prod のような環境の区別が無く、「環境の分離」はこの事象として扱う。

**区分 B: child module 化**（区分 A で root の分割を決めた後にだけ評価する）

- **B-1**: 2つ目の root が、既存の root と同じ設定種別を必要とする。root を分割する Issue の中で、共通する設定種別を child module に切り出すかを評価する。

**区分 C: 規模の再評価**（閾値を超えたら構成を見直す Issue を起票する）

| 条件 | 観測対象 | 閾値 |
|---|---|---|
| C-1 | root 直下の resource 型の異なり数（data source を除く） | 10 を超える |
| C-2 | 設定種別ファイルの数（`terraform.tf` / `providers.tf` / `variables.tf` / `locals.tf` / `outputs.tf` を除く `*.tf`） | 10 を超える |
| C-3 | root 直下の `.tf` の行数 | いずれかが 300 を超える |
| C-4 | HCP Terraform の管理リソース数（`for_each` の各インスタンスを1件と数える、組織全体） | 400 を超える |
| C-5 | GitHub API のレート制限による plan の失敗 | 1回で発火 |

見直しの Issue では、Workspace の分割と、リソースのモデリングの見直し（集約型リソースの採用など）を比べる。C-4 は組織全体で数えるので、分割しても減らない。見直しの Issue が Workspace の分割を結論した場合は、新しい ADR（または本節の改訂）として記録してから分割する。数値は仮置きであり、見直す場合は本節を改訂する。

### 3. 設定種別

**設定種別**は、GitHub 上の1つの機能に対応する設定のまとまりで、1つの設定種別ファイルで表す。1つの設定種別が複数のリソース型を使ってよく、同じリソース型が複数の設定種別に現れてよい。ただし `github_repository` の属性は、どの機能に関わるものでも設定種別 `repository` に置く（resource ブロックを複数のファイルに分割できないため。ADR 0001 の案 B）。

**基本パターン**: 1つの設定種別を1つのファイルに置き、1リポに1インスタンスを `for_each`（キーはリポ名）で展開し、属性の値は §4 の区分ごとの置き場所から resource が直接参照する。

**例外パターン**（該当する設定種別だけに適用する）:

- **1:N の集合**: 1リポに複数の要素を持つ設定種別は、全リポ共通の集合（共通集合）と、リポごとの追加分・除外分で表す。要素ごとにリソースを置く場合、インスタンスのキーはリポ名と要素の識別子から作り、リストの位置に依存させない。要素単位のリソースか、リポ単位で集合を権威的に管理する集約型のリソースかは、管理リソース数（§2 C-4）と、管理外の要素を削除してよいかで選ぶ。
- **visibility の制約**: Free プランの private リポで使えないリソースや属性は、visibility で出し分ける（§6）。
- **例外台帳の登録属性**: per-repo のフィールドを持つ（§4）。

**既知の設定種別**:

| 設定種別名 | リソース型 | 1リポあたりの基数 | visibility の制約 |
|---|---|---|---|
| `branch_protection` | `github_repository_ruleset`（target は branch） | 1:1 | public のみ（リソース単位） |
| `tag_protection` | `github_repository_ruleset`（target は tag） | 1:1 | public のみ（リソース単位） |
| `repository` | `github_repository` | 1:1 | private にも適用。使えない属性がありうる（属性単位） |
| `labels` | `github_issue_label` または `github_issue_labels` | 1:N | 無し |
| `dependabot_security_updates` | `github_repository_dependabot_security_updates` | 1:1 | 要確認 |
| `actions_permissions` | `github_actions_repository_permissions` と `github_workflow_repository_permissions` | 1:1 | 無し |

表に無い設定を足すときは、`github_repository` の属性なら `repository` に加え、それ以外は GitHub 上の機能名から設定種別名を決め（§5）、基数・visibility の制約・値の区分（§4）をこの順に決める。

### 4. 値の区分と例外台帳

#### 3つの区分

| 区分 | 定義 | 置き場所 | per-repo で変えられるか |
|---|---|---|---|
| リポ固有値 | リポの同一性や構成に由来し、方針として揃える値を持たない（例: 説明、topics、CI の job 名、visibility、類型、archived） | `repositories.<k>.<concern>.<属性>`（visibility と profile は `repositories.<k>` 直下） | 変えられる（値そのものが入力） |
| 類型決定値 | 方針として揃える値があり、それが類型（§7）で変わる | `local.<concern>_profile_defaults`（類型の識別子をキーとする表） | 例外台帳に登録した属性だけ |
| 全リポ共通値 | 方針として揃える値があり、類型を問わず同じ | `local.<concern>_preset` | 例外台帳に登録した属性だけ |

- 区分は属性ごとに、上の表の定義で判定する。リポ固有値かどうか迷う場合は、リポ固有値としない（per-repo で変えられる範囲を広げない側に倒す）。
- resource は区分ごとの置き場所から値を直接参照する。値の合成に `merge()` は使わない。
- リポ固有値のフィールドの既定値には、自然な「無し」の値（空リスト、null など）だけを使い、方針値を既定値にしない。
- 区分の変更（例: 全リポ共通値を類型決定値へ移す）は、その設定種別の通常の変更として行う。state のアドレスは変わらず、値が変わるリポの分だけ in-place update が生じる。

#### 例外台帳

特定のリポで類型決定値・全リポ共通値から外す必要が生じた場合は、per-repo のフィールドを足す前に、類型の割り当てや、類型決定値・全リポ共通値そのものの見直しで表せるかを確かめる。表せない場合に限り、例外台帳へ登録して per-repo のフィールドを持たせる。

- **登録の要件**: 類型や共通値の見直しでは表せない、差が恒常的である、差の理由を書ける、の3つをすべて満たすこと。満たさなければ、そのリポも区分の値に従う。
- **登録の手続き**: per-repo のフィールドの追加と台帳の行の追加を同じ変更で行い、所有者の承認を得る。使用リポの追加・削除も同じ手続きで行う。使用リポが無くなったら、フィールドと行を同じ変更で消す。
- **記録の粒度**: 属性単位で1行とし、元の区分、理由、使用リポとリポごとの理由、見直しの条件を記録する。台帳は README の「例外台帳」節に置く。
- **実装形**: 台帳登録属性だけ、既定値の無い `optional(T)` を置き、値が null なら元の区分の置き場所の値を使う（null フォールバック）。null だけを未指定とみなし、false・空リスト・0・空文字は per-repo の値として扱う。`coalesce` / `coalescelist` は使わない。1:N の除外分は、既定値を空集合とする `exclude` フィールドで表す。

#### 取り込み時の食い違い

GitHub 側に既にある設定を管理対象に入れるとき（import、または管理済みのリソースに未管理だった属性を加えるとき）、実値が類型決定値・全リポ共通値と異なる場合は、次のとおり扱う。リポ固有値は、実値をそのまま宣言する。

- 理由を書け、登録の要件を満たす差（理由のある差）は、例外台帳に登録し、per-repo の値として実値を宣言して取り込む。
- 過去の UI 操作の名残など、理由を書けない差（由来の無い差）は、取り込みの前に、所有者の承認を得て GitHub 側の実値を区分の値へ変える。所有者が変更しないと判断した場合は、それを理由として例外台帳に登録する。
- `local.<concern>_preset` や `local.<concern>_profile_defaults` を、食い違ったリポの実態へ寄せない。import と同じ plan で食い違う属性を in-place update することもしない（CLAUDE.md §2 は import の plan が `0 to change` であることを求める）。

1:N の集合では、共通集合に無い要素は追加分として宣言するか管理外として残すかを担当の Issue が決め、共通集合の要素がリポに無い場合は上と同じく由来で分ける（理由のある差は除外分として台帳に登録する）。

すでに管理下にある属性の方針値を変える変更は、本規則の対象外で、通常の plan のレビューを経て apply する。

### 5. 命名と配置

- **ファイル名**: 設定種別ファイルは `<concern>.tf`（`<concern>` は設定種別名）とする。設定種別に属さないファイルは `terraform.tf` / `providers.tf` / `variables.tf` / `locals.tf` / `outputs.tf` とする。
- **設定種別名**: GitHub 上の機能名を snake_case にしたもので、`github_` や `repository_` の接頭辞を付けない（`github_repository` 自体の設定種別は `repository`）。1:N の集合は複数形とし、それ以外で名前がリソース型名に由来する場合はその単数・複数に従う。1つのリソース型を複数の関心事で使う場合は `<対象>_protection` とする。
- **resource ラベル**: 設定種別名とする（例: `github_repository_ruleset.branch_protection`）。既存の `github_repository.this` はそのまま残す。
- **`repositories` のフィールド構造**: 直下には `visibility` と `profile` だけを置き、リポ固有値と台帳登録属性は設定種別名のキーの下に入れ子にする（例: `repositories.<k>.branch_protection.status_check_contexts`）。キーは、その設定種別にリポ固有値か台帳登録属性があるときだけ設ける。1:N の差分は `add` / `exclude` とする。

  ```hcl
  repositories = {
    "<repo>" = {
      visibility = "public"
      profile    = "app"

      branch_protection = {
        status_check_contexts       = ["build"]
        status_check_integration_id = 15368
      }
      labels = {
        add     = []
        exclude = []
      }
    }
  }
  ```

- **locals の名前**: `local.<concern>_<用途>` とし、用途は `preset`（全リポ共通値。1:N の共通集合を含む）、`profile_defaults`（類型決定値の表）、`targets`（visibility などで絞った `for_each` の対象）、`instances`（1:N の集合を展開した `for_each` の対象）の4つに限る。
- **locals の配置**: 1つのファイルだけで使うものはそのファイルの冒頭に、複数のファイルから参照するものは `locals.tf` に置く（公式スタイルガイド「Local values」）。

### 6. visibility による出し分け

- 適用できるかどうか（プラットフォームの制約）と、方針値（類型決定値・全リポ共通値）を別の軸として扱う。プラットフォームの制約を、類型決定値の表や per-repo のフィールドで表さない。
- リソース単位の出し分けは、設定種別ファイルの冒頭の `local.<concern>_targets` で `for_each` の対象を絞る。属性単位の出し分けは、resource の中で visibility を条件にした条件式か dynamic ブロックで行う。これは適用可否の分岐であり、例外台帳への登録を要しない。
- Ruleset（`branch_protection` と `tag_protection`）は public リポにだけ適用する。GitHub Free では private リポで Ruleset を使えない。
- private リポを管理対象にできるのは、リポ名（説明系の属性を管理する場合はその値も）が公開されてよい場合に限る。本リポは public で、`terraform.tfvars` に書いた値は公開される。

### 7. 類型プロファイル

類型の判定基準は「リポの変更がどこへ届くか」とする。

| 類型 | 識別子（`profile` の値） | 定義 |
|---|---|---|
| 配布物 | `distribution` | 第三者や所有者の他のリポが、ref で参照するか内容を複製して取り込む成果物を公開するリポ（GitHub Action、プラグイン、スキル、ライブラリ、テンプレート） |
| インフラ | `infra` | 変更が CI や IaC の実行を通じて外部の実環境（クラウド、SaaS、GitHub の設定）へ適用されるリポ |
| アプリ | `app` | 実行されるアプリケーションのソースを持ち、利用者が ref で参照も複製もしないリポ |
| ローカル構成 | `local_config` | 所有者の端末環境の構成を持ち、外部へ配布も適用もしないリポ |

- 境界例: テンプレートリポとスキル集は配布物、所有者の dotfiles はローカル構成とする。テンプレートから生成したリポは内容を複製して取り込むので、改竄された内容を所有者の側では回収できない。
- 1つのリポには類型を1つだけ宣言する。複数の類型に当たるリポは、**配布物 > インフラ > アプリ > ローカル構成** の順で最も上位の類型を選ぶ。
- どの類型にも当たらないリポは最も近い類型を選び、1つに決められなければ本 ADR を改訂して類型を足す。
- 選んだ類型の値からそのリポだけ外したい属性は、§4 の例外台帳で扱う。同居リポの中でパスによって扱いを変えたい差は、Ruleset の外（HCP のトリガー条件、CI の集約ジョブなど）で吸収する。
- `profile` は `repositories.<k>` 直下の必須フィールドで、既定値を持たず、上の4つの識別子以外を validation で拒否する。
- `local.<concern>_profile_defaults` は4つの識別子すべてをキーに持ち、全類型が同じ属性の集合を持つように作る。類型ごとの具体値は、各設定種別を実装するときに決める。

## 根拠

### 1. 単一 root module

- 公式ドキュメント「When to write a module」は、単一のリソース型の薄い包装にあたる module を勧めていない（"We *do not* recommend writing modules that are just thin wrappers around single other resource types."）。本リポの設定種別は、どれも管理リポごとに同じ設定を置くもので、module で包むとこの形になる。
- 管理リポの増減は `for_each` が吸収し、module を増やす必要が無い。共通部分を切り出しても、使う root は1つしかない。
- 公式スタイルガイド「Multiple environments」は、HCP Terraform の利用者には環境や規模への対処として Workspace の分割を勧めている。このため §2 は root / Workspace の分割と child module 化を区別する。

### 2. 発動条件

- 行数やファイル数が増えたこと自体は分割の理由にならない。閾値の超過を分割に直結させると誤った分割を招くので、分割は事象（区分 A）に結び付け、定量の閾値は見直しの Issue を起票する条件（区分 C）に留める。
- 区分 B を区分 A の後にだけ評価するので、1つの事象から「root の分割」と「child module 化」が別々の行動として並び立たない。
- 閾値は、予定している設定種別がすべて入った後の見込み（resource 型 6、設定種別ファイル 6〜7）に 1.5〜2 倍の余裕を取った。C-4 の 400 は HCP Terraform Free の上限（500 managed resources）の 80% である。

### 3. 設定種別

- 公式スタイルガイド「File names」は、リソースを論理的なグループでファイルに分け、定義の場所がすぐ分かることを求めている。設定種別はこの論理的なグループにあたる。リソース型の単位で分けると、`github_repository_ruleset` が branch 保護とタグ保護にまたがり、関心事の局所性が失われる。
- 既知の設定種別名を ADR で確定しておかないと、後続の Issue で名前が揺れる（実際に README の例と Issue の本文で `repository_labels.tf` と `labels.tf` に分かれていた）。
- 1:N の集合を `optional()` の既定値で持つと、per-repo で指定した時点で集合全体が置き換わり、追加・除外の差分を表せない。

### 4. 値の区分と例外台帳

- 所有者の方針（コンテキスト）に従い、値を類型ごとの型に収め、差がどこに・なぜあるかを台帳の1か所で読めるようにする。
- 置き場所が区分に一対一で決まるので、作業者もレビュアーも規則だけで配置を判定できる。類型決定値の表と全リポ共通値が同じファイルの冒頭に並び、設定種別の方針全体を1か所で読める。
- ADR 0001 が `local.*_preset` を採らなかった理由は、`merge()` の戻り値が `map(any)` になり型検査を失うことだった。locals の object を resource から直接参照すれば、存在しない属性の参照は `terraform validate` が拒否し、値の型は provider のスキーマで検査される。
- `optional()` の既定値は、同じ object の別のフィールドも別の変数も参照できない（2026-09-26、Terraform v1.15.6 で `Error: Variables not allowed` を確認）。このため、類型で変わる値を variable defaults で解決することはできず、類型決定値は locals の表から参照する必要がある。
- null だけを未指定とみなすのは、偽値（false、空リスト、0、空文字）を未指定と取り違える合成を防ぐためである（ADR 0002 の案 B で議論した問題と同じ種類）。
- 取り込み時の食い違いを由来で分けると、台帳を恒常的な例外だけに保てる。代償として、取り込み前の実値の変更は Terraform の plan を経ないので、所有者の承認と Issue への記録で追跡する。

### 5. 命名と配置

- Ruleset が branch 用と tag 用の2本になると、`enforcement` などのフィールド名がフラットな構造では衝突する。設定種別ごとに入れ子にすれば衝突が構造的に起きず、「設定種別名＝ファイル名＝フィールド群のキー」が対応する。
- locals の用途名を4つに固定すると、作業者が名前を ADR だけで決められる。

### 6. visibility による出し分け

- 類型と visibility は互いに独立なので、「private なら無効」を類型決定値の表で表すと、同じ類型の private リポで破綻する。per-repo のフィールドで表すと、制約を外せてしまう。
- 適用対象の集合を設定種別ファイルの冒頭に置くと、制約がそのファイルの中で閉じる。

### 7. 類型プロファイル

- 類型決定値の主な差（タグ保護、Actions 権限）は、変更が届く先で決まる。判定基準を固定すると、誰が判定しても同じ類型になる。
- インフラの被害は所有者が管理する実環境の中に閉じ、所有者が復旧手段を持っている。配布物の被害は利用者の環境へ届き、所有者の側では回収できない。このため配布物を最上位にする。
- `profile` を必須にすると付け忘れを構造的に防げ、`visibility` と同じ扱いになる。

## 代替案

- **child module 化（設定種別ごとに module を作る）**: state・影響半径・App 権限は変わらず、単一のリソース型の薄い包装になる。
- **private リポの定義を HCP の変数や非公開の別リポへ分ける**: PR のレビュー経路を失うか、root が2つになり運用コストに見合わない（#4 のコメントで却下）。
- **発動条件を定量の閾値だけで定める**: 閾値の超過が分割に直結し、誤った分割を招く。
- **リソース型ごとにファイルを分ける**: 関心事の局所性が失われ、Ruleset のファイルが膨らむ。
- **類型既定値 → per-repo override の2段（全属性で上書きを許す）**: 所有者の方針に反する。
- **全リポ共通値を `repositories` のフィールド既定値に置く（ADR 0001 の形）**: per-repo の上書き経路そのもので、例外台帳の制度と両立しない。類型で変わる値も置けない。
- **類型ごとに `repositories` を別の map に分け、それぞれに既定値を書く**: object 型の定義を類型の数だけ複製し、属性を1つ足すたびに4か所を直すことになる。
- **全リポ共通値・類型決定値を型付き variable の既定値に置く**: `terraform.tfvars` や HCP の変数から上書きできる別の経路ができ、正とする記述場所が2つになる。
- **`merge()` で合成する**: 型を失い、重ねる順序が暗黙の優先順位になる。
- **全リポ共通値を resource の引数にリテラルで書く**: 共通値が resource の中に散らばり、類型決定値の表と並べて比べられない。
- **取り込み時の食い違いをすべて台帳に恒久登録する**: 取り込み時点の実態がそのまま例外として固定され、型にはめる方針が取り込みのたびに崩れる。
- **取り込みの後に Terraform で区分の値へ寄せる**: 変更がすべて plan を通るが、取り込みのたびに台帳の暫定行とフィールドを足しては消すことになる。
- **フラットなフィールド構造のまま、衝突するものだけに接頭辞を付ける**: 接頭辞の要否がフィールドごとに揺れる。
- **visibility の適用可否を中央の表（`locals.tf`）に置く**: 設定種別を足すたびに2つのファイルを触ることになる。
- **類型の判定基準を「リポが保持する権限や秘密」にする**: 配布物とアプリの区別が基準に現れず、タグ保護の対象を決める根拠にならない。
- **既定の類型を置く、または「類型なし」を許す**: 付け忘れたリポに方針が黙って適用されるか、表ごとに「類型なし」の行が要る。
- **複数の類型を重ねる（`merge()` による重ね合わせ、属性ごとに厳しい方を採る、複合類型を列挙する）**: 優先順位の暗黙化、厳しさの順序の定義、型の組み合わせ爆発のいずれかを招く（#32 のコメントで却下）。

## 帰結

- 既存の `branch_protection.tf`（`merge()` による合成、ADR 0002）と `repository.tf`（`repositories` のフィールド既定値、#16 で導入・apply 済み）は、本 ADR の値の区分に従っていない。両者を本 ADR の置き場所へ移す移行 Issue を、本 ADR の承認後に起票する。移行は `terraform plan` が No changes であることを確かめながら進める。
- 現行の `terraform.tfvars` にある per-repo の上書き（`has_wiki`、`delete_branch_on_merge`）は、移行の際に §4「取り込み時の食い違い」の規則で扱う（例外台帳への登録か、実値の変更か）。
- `variables.tf` に残る branch protection の未使用の上書きフィールドは、移行までの間も使わない。使う必要が生じた場合は例外台帳への登録を経る。
- 管理対象リポの visibility を切り替えると、§6 により Ruleset のインスタンスが create / destroy される。private の Free リポに Ruleset が残らない切り替えの手順は、Ruleset の適用対象を visibility で絞る実装（`local.<concern>_targets`）を入れる Issue で定め、README に置く。
- reviewer（`terraform-design-reviewer`）の観点6は、ADR 0001 の variable defaults パターンを正としているため、本 ADR の承認後に改訂する。
- 設定種別を足す後続の Issue（ラベル、Dependabot、Actions 権限、タグ保護、類型の宣言など）は、本 ADR の §3〜§7 に従う。

## ロールバック可能性

- §1・§2 は文書だけの決定で、本 ADR の改訂で戻せる。
- ファイル名を変えても state のアドレスは変わらない。resource ラベルを変える場合は `moved` ブロックが要る。
- 例外台帳の制度や値の置き場所（`repositories` のフィールド既定値への回帰を含む）、フィールドの入れ子を戻す変更は、型定義・locals・`terraform.tfvars` の書き換えで済み、state は変わらない。ただし `optional()` の既定値からは類型を参照できないので、類型で値が異なる属性は各リポに値を書く形になる。
- 取り込み前に GitHub 側で変えた実値は、規則を戻しても戻らない。取り込み Issue に記録した変更前の値へ戻す。
- visibility による適用対象の集合を変えると、Ruleset のインスタンスの create / destroy が生じる。
- リポの類型を変えると、新旧の類型で値が異なる類型決定値だけが変わる。

## 再評価の条件

- `optional()` の既定値で、同じ object の別のフィールドや別の変数を参照できるようになった場合（§4 の前提が消える）。
- GitHub Free で、private リポに Ruleset を使えるようになった場合（§6 の前提が消える）。
- 例外台帳の行数が増え続け、類型の定義の見直しが要ると判断される場合。
