# ADR 0011: 現行の設計規則を設計仕様書へ移し、取り込み時の方針値の見直しを条件付きで許す

## ステータス

承認（2026-09-27、[#102](https://github.com/kuchita-el/github-config/issues/102)）

本 ADR は、[ADR 0004](0004-terraform-module-structure-policy.md) 決定 §4「取り込み時の食い違い」の3項目目のうち、`local.<concern>_preset` / `local.<concern>_profile_defaults` を食い違ったリポの実態へ寄せることを一律に禁じる判断を改め、方針値の見直しを条件付きで許す（決定 2）。同じ項目の「import と同じ plan で食い違う属性を in-place update しない」は維持する。あわせて、ADR 0004 決定 §1〜§7 が定める現行の設計規則の正本を、設計仕様書 [`docs/design/terraform-structure.md`](../design/terraform-structure.md) へ移す（決定 1）。

ADR 0004 の本文は変更しない。改めた判断は本 ADR に記録する（[ADR 0009](0009-tag-protection.md) 決定 §2・[ADR 0010](0010-vulnerability-alerts-and-dependabot-security-updates.md) 決定 §3 と同じ方法）。

## コンテキスト

[#102](https://github.com/kuchita-el/github-config/issues/102) は、次の3つの問題を扱う。

1. ADR 0004 §4「取り込み時の食い違い」は、GitHub 側の実値が類型決定値・全リポ共通値と異なる場合を、理由のある差（例外台帳への登録）と由来の無い差（取り込みの前に GitHub 側の実値を変える）の2通りに振り分け、3項目目で `local.<concern>_preset` / `local.<concern>_profile_defaults` を食い違ったリポの実態へ寄せることを禁じている。しかし取り込みの過程では、方針値そのものが誤っている、あるいは古くなっていると分かる場合がある。一律に禁じると、こうした知見を方針へ戻す経路が規則の上で塞がれる。
2. 現行の設計規則（module 構成、構成を見直す条件、設定種別、値の区分と例外台帳、命名と配置、visibility による出し分け、類型プロファイル）は ADR 0004 の決定節にしか書かれておらず、README・CLAUDE.md・コードのコメントが「ADR 0004 §N に従う」と ADR を現行規則として参照している。ADR は決定の記録であり、現行規則の置き場ではない。規則を改めるたびに ADR の置き換えを重ねると、現行規則を知るために複数の ADR を読み合わせる必要が生じる。実際に ADR 0004 §3「既知の設定種別」表は、ADR 0010 決定 §3 が本文を変えずに更新しており、現行の表を知るには2つの ADR を突き合わせる必要があった。
3. CLAUDE.md §2 手順2 は「`terraform.tfvars` / `branch_protection.tf` を実態へ寄せる」とだけ書いており、食い違いの振り分けが反映されていない。

以下、食い違いの扱いを次の3つで呼ぶ。

- (a) 取り込みの前に、所有者の承認を得て GitHub 側の実値を区分の値へ変える
- (b) 例外台帳に登録し、per-repo の値として実値を宣言して取り込む
- (c) 方針値（`local.<concern>_preset` / `local.<concern>_profile_defaults`）そのものを見直す

(a) には先例がある。[#4](https://github.com/kuchita-el/github-config/issues/4)・[#7](https://github.com/kuchita-el/github-config/issues/7) の取り込みでは、gachanuma・cody・coffeeshop などの実値を、取り込みの前に所有者の承認を得て区分の値へ変えてから import した（#7 については ADR 0010 のコンテキスト節）。[#73](https://github.com/kuchita-el/github-config/issues/73) でも、4リポの Actions 権限の実値を先に決定値へ変えてから取り込んだ（[ADR 0008](0008-actions-permissions.md) 決定 §2）。

本リポの所有者（kuchita-el）は 2026-09-27 に、(c) を条件付きで許すこと、判定の順序、現行規則を設計仕様書へ移すこと、仕様書の改訂で ADR を要する範囲を決めた。

## 決定

### 1. 現行の設計規則の正本を設計仕様書にする

現行の設計規則の正本を [`docs/design/terraform-structure.md`](../design/terraform-structure.md)（以下、仕様書）とし、ADR は決定とその理由の記録に限る。

- **移設の範囲**: ADR 0004 決定 §1〜§7 を、節番号を揃えて、意味を変えずに仕様書へ移した。規定の意味を変えたのは、§4「取り込み時の食い違い」への (c) と判定の順序の追加（決定 2）だけである。
- **後続の ADR による更新の反映**: 後続の ADR が ADR 0004 の本文を変えずに明示的に更新した内容も、現行規則として仕様書に反映した。ADR 0010 決定 §3 による §3「既知の設定種別」表の更新（`dependabot_security_updates` 行の visibility の制約を「要確認」から「無し」へ改め、`vulnerability_alerts` 行（`github_repository_vulnerability_alerts`、1:1、無し）を加える）を、仕様書 §3 の表に反映した。仕様書の冒頭に、節ごとに決定を記録した ADR の対応表を置く。
- **例外台帳の置き場所**: README の「例外台帳」節にあった台帳の表を、仕様書 §4「例外台帳」の末尾へ移した。台帳は、登録の要件・手続きと同じ場所に置く。
- **改訂手続き**: 仕様書の規定を変える変更のうち、次のいずれかに当たるものは、決定を ADR（`docs/adr/`）に記録し、同じ変更で仕様書を改訂する。(1) 複数の設定種別や後続の変更を縛る構造・原則の変更（値の区分の体系、類型の追加、root module や Workspace の分割など）。(2) 却下した案とのトレードオフを残す価値がある変更。それ以外の変更（表の行、閾値、1属性の方針値、表現の整理など）は仕様書の改訂 PR だけで行い、理由はその PR に書く。いずれに当たるか迷う場合は ADR を書かない。例外台帳の行の追加・削除は仕様書 §4「例外台帳」の登録の手続きに従う。この手続きは仕様書の冒頭にも定める。
- **ADR 0004 決定節の自己参照の読み替え**: ADR 0004 の決定節には、ADR 0004 自身の改訂を求める記述が3つある。仕様書では、これらを上の改訂手続きに沿って次のとおり読み替えた。

| ADR 0004 の記述 | 仕様書での扱い |
|---|---|
| §2 末尾（L62）「見直しの Issue が Workspace の分割を結論した場合は、新しい ADR（または本節の改訂）として記録してから分割する」 | (1) に当たる。決定を新しい ADR に記録し、同じ変更で仕様書を改訂してから分割する（仕様書 §2） |
| §2 末尾（L62）「数値は仮置きであり、見直す場合は本節を改訂する」 | 仕様書 §2 の改訂だけで行い、ADR を要しない（仕様書 §2） |
| §7（L173）「1つに決められなければ本 ADR を改訂して類型を足す」 | (1) に当たる。決定を ADR に記録し、同じ変更で仕様書を改訂して類型を足す（仕様書 §7） |

- **層ごとの配置**: 取り込み時の食い違いに関わる記述を、次の層に分けて置く。判定の基準は仕様書だけに書き、他の層は再掲せず仕様書を参照する。

| 層 | 内容 | 配置 |
|---|---|---|
| 判定 | 現行の設計規則。取り込み時の食い違いの振り分け（(c) を含む）と例外台帳の表 | 仕様書 |
| 手順 | 取り込みの作業順序（(c) は import より前の別 PR、import の PR は `0 to change`） | `README.md`「既存リポの取り込み（import）」節 |
| 強制 | Claude が方針値・`terraform.tfvars` を自分の判断で実態へ寄せないこと | `CLAUDE.md` §2 手順2 |
| 決定の記録 | 決定の理由と却下した案 | ADR（`docs/adr/`） |

### 2. 取り込み時の方針値の見直し（(c)）を条件付きで許す

仕様書 §4「取り込み時の食い違い」に、次のとおり定める。条文は仕様書を正本とし、以下はその要旨である。

- (a)・(b) を原則とする。(c) は、その区分に属する全リポに通じる理由がある場合に限り行う。
- **判定の順序**: 差ごとに、次の順に扱いを決める。
  - ① 差の理由を書けない（過去の UI 操作の名残など、由来の無い差）場合は (a) とする。所有者が変更しないと判断した場合は、それを理由として (b) とする。
  - ② 差の理由を書け、その理由がその区分に属する全リポ（全リポ共通値なら全管理リポ、類型決定値ならその類型の全リポ）に通じ、方針値の誤り・陳腐化を示す場合は、(c) を所有者へ提案する。所有者が承認しなければ ③ へ進む。
  - ③ ①・② に当たらない差と、② で所有者が (c) を承認しなかった差は、登録の要件（仕様書 §4「例外台帳」）を満たせば (b) とする。満たさなければそのリポも区分の値に従い、(a) と同じく取り込みの前に GitHub 側の実値を変える。② で (c) が承認されなかった差は、方針値の見直しで表せるため、登録の要件（類型や共通値の見直しでは表せない）を満たさない。
- **(c) の条件と手続き**: 取り込むリポの実態に合わせることだけを理由とする (c) は行わない。(c) は、すでに管理下にある属性の方針値を変える通常の変更として、import より前の別 PR で行う。その PR の plan で他リポに生じる change を確認し、所有者の承認を得て apply する。
- **import の PR**: import の PR の plan は `0 to change` を保つ。import と同じ plan で食い違う属性を in-place update しない（CLAUDE.md §2 の要件は緩めない）。
- **1:N の集合**: 共通集合の要素がリポに無い場合も、同じ判定の順序で振り分ける（(b) では除外分として台帳に登録し、(c) では共通集合を見直す）。ADR 0004 の「上と同じく由来で分ける」を、この順序による振り分けへ改めた。

## 根拠

### (c) を条件付きで許す

- (c) は、取り込みで得た知見を方針値へ戻す経路になる。一律に禁じたままでは、方針値の誤りや陳腐化に気付いても、規則の上ではそのリポを (a) か (b) に振り分けるしかない。
- 条件（その区分に属する全リポに通じる理由がある）により、取り込むリポの事情だけによる方針値の変更は (c) から外れ、③ で (b) か区分の値への変更に振り分けられる。取り込みのたびに方針値が取り込むリポの実態へ寄ることはなく、類型ごとの型にはめるという所有者の方針（ADR 0004 コンテキスト）を保てる。

### (c) を import より前の別 PR で行う

- 方針値の変更を別 PR にすると、他リポへの影響（in-place update）がその PR の plan に単独で現れ、所有者の承認の対象が明確になる。
- import の PR は `0 to change` を保てるので、CLAUDE.md §2 の「import の plan は `0 to change`」要件を緩めずに済む。

### 判定の順序で ② を ③ の前に置く

- ADR 0004 §4「例外台帳」は、per-repo のフィールドを足す前に、類型決定値・全リポ共通値そのものの見直しで表せるかを確かめ、表せない場合に限り台帳へ登録すると定めている。② を ③ の前に置くのは、この既存の規則に従った順序である。
- ② で (c) が承認されなかった差が登録の要件を満たさないとする ③ の末文も、新しい規則ではなく同節から導かれる。登録の要件の第1項「類型や共通値の見直しでは表せない」が問うのは、見直しで表せるかであり、見直しが採られたかではない。所有者が変更しないと判断した差を (b) に登録する経路は、ADR 0004 §4 のとおり由来の無い差（①）にだけある。

### 現行規則を設計仕様書へ移す

- 現行規則の正本が1か所になり、作業者・レビュアーが仕様書だけを読んで判定できる。後続の ADR による更新（ADR 0010 決定 §3 など）を読み合わせる必要が無くなる。
- ADR は決定時点の記録として不変に保てる。規則を改めても、承認済みの ADR の本文を変えずに済む。
- 節番号を ADR 0004 の決定に揃えることで、コードやドキュメントに残る「ADR 0004 §N」の根拠の参照と、仕様書の節との対応が保たれる。

### 仕様書の改訂手続き

- ADR を要する変更を、構造・原則を動かす判断（(1)）と、却下した案とのトレードオフを残す価値がある判断（(2)）に限る。
- 表の行・閾値・1属性の方針値のような項目単位の変更は、理由がその改訂 PR に残るため ADR を課さない。仕様書の保守を重くしない。
- 類型の追加や root module の分割のように後続の変更を縛る判断は、理由を残すかどうかを作業者の判断に委ねず、ADR に残す。

## 代替案

### (c) を一律に禁じたままにする

ADR 0004 の規則を変えずに済み、方針値が取り込みで動くことが無い。

**採用しなかった理由**: 取り込みで方針値の誤りや陳腐化に気付いても、その知見を方針へ戻す経路が規則の上で塞がれる。

### (c) を条件なしに許す

食い違いを見つけた時点で、方針値を自由に見直せる。

**採用しなかった理由**: 取り込みのたびに方針値が取り込むリポの実態へ寄り、類型ごとの型にはめるという所有者の方針が崩れる。

### (c) を import と同じ PR で行う

PR が1本で済む。

**採用しなかった理由**: import の plan が `0 to change` にならず、CLAUDE.md §2 の要件に反する。方針値の変更による他リポの change が取り込みの差分に紛れ、所有者が承認の対象を見分けにくくなる。

### ADR 0011 で ADR 0004 §4 を置き換え、各所は ADR を参照し続ける（当初案）

新しい文書を作らずに済み、既存の参照を張り替える必要も無い。

**採用しなかった理由**: 規則を改めるたびに ADR の置き換えが重なり、現行規則を知るのに複数の ADR を読み合わせる必要が生じる。ADR 0004 §3 の表は、すでに ADR 0010 決定 §3 との読み合わせが要る状態になっていた。

### ADR 0004 の本文を改訂する

現行規則が ADR 0004 の1か所に保たれ、参照を張り替えずに済む。

**採用しなかった理由**: 承認済みの ADR の本文を変えない制約に反し、決定時点の記録が失われる。

### ADR 0004 のステータス節に置き換えの注記を入れる

ADR 0004 を読んだ人が、改められた判断に気付ける。

**採用しなかった理由**: ステータス節も ADR 0004 の本文であり、変えない。改めた判断は、改めた側の ADR のステータス節に記す（ADR 0004 自身も、ADR 0001・0005 の置き換えを自身のステータス節に記している）。

### 現行規則を ARCHITECTURE.md に置く

構成の説明を1つの文書に集められる。

**採用しなかった理由**: 構成の概観を置く文書であり、属性ごとの区分や取り込み時の判定のような規則とは抽象度が合わない。

### 現行規則を README に置く

新しいディレクトリを作らずに済み、利用者が最初に読む文書に規則が載る。

**採用しなかった理由**: README は入口であり、判定（仕様書）と手順（README）を層ごとに分けて置く配置（決定 1）に反する。

### 仕様書に ADR 0004 の根拠・代替案も移す

規定とその理由を1つの文書で読める。

**採用しなかった理由**: 決定の理由は記録である ADR に残す。仕様書に収めるのは決定 §1〜§7 の規定であり、理由まで移すと、決定時点の記録と現行規則の区別が崩れる。

### 仕様書の規定の意味を変える変更はすべて ADR を要するとする

規定を変えた理由が、すべて ADR に残る。

**採用しなかった理由**: 表の1行・閾値1つ・1属性の方針値のような項目単位の変更にまで ADR を課し、仕様書の保守を重くする。所有者も、項目単位の変更で ADR を書くことに違和感を示した。

### ADR は常に任意とし、仕様書の改訂 PR だけで規定を変えられるようにする

仕様書の保守が最も軽くなる。

**採用しなかった理由**: 類型の追加のように後続の変更を縛る判断の理由が、残るかどうか作業者次第になる。

## 帰結

- CLAUDE.md・README・コードのうち、ADR 0004 を現行規則として参照する記述（規範の参照）は仕様書へ向ける。根拠としての参照と ADR の本文は、ADR 0004 を指したまま残る。
- terraform-design-reviewer（`.claude/agents/terraform-design-reviewer.md` と `docs/agents/terraform-design-reviewer/`）は変えておらず、観点 6 は引き続き ADR 0004 を一次情報として読む。reviewer の役割の見直しは [#103](https://github.com/kuchita-el/github-config/issues/103) で扱う。
- ADR 0005・0007〜0010 に残る現行規則は、仕様書へ移していない。移設は別 Issue で扱う（起票は所有者の承認後）。
- (a) が Terraform の plan を経ない点は見直していない。取り込みの前の実値の変更は、引き続き所有者の承認と Issue への記録で追跡する。
- (c) を行うと、その区分に属する他リポに in-place update が生じる。影響は (c) の PR の plan で確認する。
- ADR を要しない仕様書の改訂（表の行、閾値、1属性の方針値、表現の整理など）の理由は、ADR ではなく改訂 PR に残る。

## ロールバック可能性

- 本 ADR の変更は文書とコメントだけで、Terraform の state は変わらない。
- (c) で変えた方針値は、戻す変更を方針値の通常の変更として行う（通常の plan のレビューを経て apply する）。

## 再評価の条件

- 同じ区分で、(c) の提案が取り込みのたびに繰り返される場合（類型の定義や方針値の決め方の見直しが要る）。
- `docs/design/` に別の仕様書を置く必要が生じた場合（仕様書の範囲の見直し）。
- あわせて、仕様書の改訂で ADR を要する手続き（決定 1 の (1)(2)）が、理由を残す価値に見合っているかを見直す。
